# Review checklist

Reviewers and authors use the same list. A plugin that fails an item is not necessarily rejected; the
item is discussed.

## Honesty
- [ ] The description says what the plugin does, in one line, without marketing.
- [ ] `[permissions]` matches the code: programs it runs, whether it uses the network, where it writes.
- [ ] No telemetry, no phoning home, no update checks of its own.
- [ ] No downloading and executing code at runtime. Prebuilt binaries use `https` URLs with a SHA-256
      and have public source.

## Safety
- [ ] Read every file of the plugin. Shell snippets run in the user's shell: nothing unexpected (no
      `eval` of remote data, no changes to unrelated dotfiles, no PATH hijacking).
- [ ] Scripts quote variables, handle spaces in paths and fail quietly instead of printing errors in the prompt.
- [ ] Hooks and commands do not delete or overwrite user files outside their own purpose.

## Quality
- [ ] `shellcraft plugin check` passes; segments run in well under 50 ms or use `when` and `ttl_ms` well.
- [ ] Works in each shell the manifest claims; the rest are excluded with `shells = [...]`.
- [ ] A name that does not collide with a built-in command, another plugin or a common tool.
- [ ] `license` is set and compatible with MIT for anything copied.
- [ ] The version was raised and the index regenerated by `scripts/publish.sh`.

## Documentation
- [ ] The README or description tells a new user what they get and how to turn it off
      (`shellcraft remove <name>`).
